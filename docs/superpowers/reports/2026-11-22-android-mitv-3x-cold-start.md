# 小米电视全屏播放从 1× 直切 3× 的冷启动复测

小米 MiTV-MTTP0，Android 9 / API 28，32 位 ARM。同一 APK 完成本地文件一次、HTTP 三次独立进程冷启动。每次分别在暂停恢复至 1× 后、连续以 1× 播放 10 秒后直切 3×，两次切换间均回到隧道播放。全程使用同一段 320 × 180 AVC/AAC 素材，HTTP 由本机回环服务器提供。[机器可读结果](evidence/2026-11-22-android-mitv-3x-cold-start/results.json) · [真机与构建回执](evidence/2026-11-22-android-mitv-3x-cold-start/captures.tar.xz)

## 结果

## 定位与修改

原 APK 的三轮 HTTP 冷启动曾观察到一次 2.7326×。本次重新采集原 APK，两次切换均速为 2.7739 / 2.7630。第一次切换时，MStar AVC 切换输出 Surface 后约 188 ms，PCM 音轨才配置完成。设备当时记录了约 9 秒可播放的缓冲。[前次三轮完整测量](2026-11-22-android-mitv-cold-speed-and-hls-recovery.md)

第一版 HTTP 两次直切达到均速门槛，但第二次观察到 AVC 连续配置两次，首帧耗时 899 ms。本地对照也出现两次配置，第二次均速 2.7165×，未达到门槛。最终版本在选轨已退出隧道、渲染器还未收到 3× 速率时，给速率消息最多 50 ms 到达。超过这个时间走常规解码器初始化。初版对照保留在结果文件。

在这台电视的未加密渐进式点播路径上，播放器请求 3× 且已退出隧道时，MStar AVC 解码器在独立工作线程配置。播放线程同时为新音轨预填 PCM，并在原生解码器准备就绪后接管。Surface、格式、速度变更以及跳转、停用和释放都会清理待接管的解码器。起步音频队列仍按 150 毫秒实际播放时长预填。

修复包时间取设备切档命令标记至原生日志的间隔。原包没有该标记，以 12 秒窗口末尾的采样日志回推，绝对延迟为近似值。首帧取当前 Surface 的原生回调。音频位置取 AudioTrack 服务端帧计数。音频起动取 Media3 在播放头推进后回报的 `playoutStartSystemTimeMs`，按同一设备的命令时钟换算。素材音轨为静音。

## 复测方式

编译示例的 `integration_test/android_tv_playback_test.dart`，指定 `YL_TV_CASE=speed-cold`。每轮在示例应用的 `code_cache/yl_tv_speed_case` 写入 `speed-http` 或 `speed-file`，停止示例进程后重新启动。验收核对进程号、实际执行的用例名、安装 APK 和 Dart 内核哈希。本地对照末段 ADB 离线。通过独立 ADB 服务重新连接后，原 PID 15086 仍在运行，按相同的系统日志时间戳补回第二次切档数据和整套通过回执。

测试 APK SHA-256 为 `d08ec02c5eeb25080fdfaec93d2274202970e24e819ddd35d5817bb30017d17b`。Android 原生回归 646 项通过，3 项跳过，Dart 静态检查通过。收尾已移除本轮测试选择文件、恢复原示例 APK，核对 TVS 1.2.7 正式包并返回前台。
