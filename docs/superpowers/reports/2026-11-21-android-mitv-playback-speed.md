# 小米电视 API 28 倍速播放复测

Xiaomi MiTV-MTTP0，Android 9 / API 28，32 位。两种输入共用同一份 Debug APK，安装包和设备回读 SHA-256 一致。使用公开 Flutter 播放器和同一段 320 × 180、24 fps 的 AVC/AAC MKV。HTTP 由主机提供，通过局域网 ADB 转发，支持 HTTP/1.1 字节范围请求。实际倍速取公开媒体位置增量除以单调时钟时长。

## 2026-11-22 全屏 3× 起步音频欠载复测

在同一台小米电视上，用同一份 320 × 180 AVC/AAC 样片测试本地文件和受管 HTTP。每种输入分别在暂停恢复到 1× 后、连续播放 1× 十秒后直切 3×。从公开切档命令返回起采样 12 秒，继续按 2.75× 至 3.25× 校验，并要求从命令发起前到采样结束的音频欠载计数保持不变。

两轮复测使用相同 APK。第一轮沿用原来的周期性进程内存采样，第二轮只在释放后取内存读数，两轮均采集硬件图层和 HTTP 回执。

| 轮次 | 输入 | 两次直切实际倍速 | 两次切换首帧延迟 | 两次直切新增欠载 | 会话累计欠载 |
| --- | --- | --- | --- | --- | ---: |
| 1 | 本地文件 | 2.7737× / 2.8023× | 720 / 548 ms | 0 / 0 | 0 |
| 1 | 受管 HTTP | 2.7964× / 2.7702× | 644 / 677 ms | 0 / 0 | 0 |
| 2 | 本地文件 | 2.7674× / 2.7979× | 509 / 652 ms | 0 / 0 | 0 |
| 2 | 受管 HTTP | 2.7590× / 2.7631× | 766 / 605 ms | 0 / 0 | 0 |

两轮完整集成用例均通过。8 次直切都达到原倍速区间，所有会话的累计音频欠载均为 0。

该机 3× 新建 PCM 音轨的起步缓冲按实际播放时间预填最多 150 毫秒，48 kHz 下从 6,000 增至 21,600 帧。音轨收到播放请求后等待实际 PCM 写入，达到目标或底层无法继续写入时开始播放。硬件播放头推进或累计接收字节超过起步队列容量后，才扩展至 54,000 帧的稳态容量，48 kHz 下相当于 3× 时 375 毫秒的播放余量。常规档位保留原有容量，额外内存仍受原有 256 KiB 上限约束。Media3 每轮先给音频解码器和音轨补数据，再处理同步视频解码。同步视频解码器等待 3× 首帧时将轮询间隔缩至 2 毫秒，最长持续 500 毫秒，首帧到达即恢复常规调度。

同机对照中，单独增加缓冲至 14,400 帧时，两种输入的第一次直切分别为 2.7374×、2.7496×。调整视频重接后的 HTTP 有一次为 2.7484×，改用异步 AVC 解码的本地第二次为 2.7268×。80 毫秒搭配音频优先的对照仍出现 1 次 HTTP 起步欠载。100 毫秒的前一版本在常规播放下四次均通过。周期性采样下 HTTP 第二次直切仍有 1 次欠载，原生回调显示距上次补充 PCM 已过 128 毫秒。这些对照均计入回执。

第一轮主机空闲休眠 66 秒，期间设备继续播放，ADB 的后续日志在唤醒后补齐。该轮 HTTP 的两次合成器快照都落在回到 1× 后，第二轮同包复核了 HTTP 的 3× 和 1× 图层。另一次常规对照因主机休眠而在 HTTP 起播前超时，完整重跑时让主机保持唤醒。这个中断样本单独保留。

每次直切后恢复 1× 均继续播放。电视合成器确认两种输入在 3× 与回到 1× 时，视频图层均为 1920 × 1080。设备安装包回读 SHA-256 与构建一致，每轮释放后视频解码器持有数为 0。

## 全屏显示与 1× 直切 3× 复测

修复前电视合成器报告屏幕为 1920 × 1080，实际视频图层仅在左上角占 640 × 360。Flutter 之前在绘制时放大画面，电视的原生 SurfaceView 仍按样片尺寸布局。现在依据播放器视口、视频宽高比、旋转和适配模式直接设置原生视图的布局尺寸。两种输入在 3× 和恢复 1× 时的视频硬件图层均覆盖 (0, 0) 到 (1920, 1080)。本轮使用同一段 320 × 180 样片等比放大。[本地播放实机截图](evidence/2026-11-21-android-mitv-playback-speed/fullscreen.png)

每种输入执行两次直切。第一次在暂停恢复后切档，第二次先连续播放 1× 十秒。实际倍速沿用原有窗口，从公开切档命令返回后采样 12 秒，下限为 2.75×。首帧延迟从发起命令前的设备单调时钟计至当前 Surface 的首帧回调。首个媒体秒耗时取首次观察到播放位置推进至少一秒的时间。

| 输入 | 切换时机 | 前 12 秒实际倍速 | 首帧 | 推进首个媒体秒 | 切回 1× 后前 10 秒 |
| --- | --- | ---: | ---: | ---: | ---: |
| 本地文件 | 暂停恢复后 | 2.7877× | 460 ms | 1123 ms | 0.960× |
| 本地文件 | 连续播放后 | 2.7706× | 692 ms | 1282 ms | 0.946× |
| 受管 HTTP | 暂停恢复后 | 2.7548× | 517 ms | 1173 ms | 0.972× |
| 受管 HTTP | 连续播放后 | 2.7690× | 510 ms | 1149 ms | 1.005× |

两个用例均通过。1.5×、2×、连续切档、暂停跳转和重挂视图也通过。3× 稳态实测为本地 3.047×、HTTP 3.002×。六个稳态窗口均无新增音频欠载或重缓冲。两个会话的累计音频欠载分别为 0、5 次。释放后同一进程持有 0 个视频解码器。

HTTP 的 5 次欠载都出现在第一次从 1× 直切 3× 的前 12 秒。样片的 AAC 音轨为静音，计数来自播放器。

该机新建的 3× PCM 音轨以 6,000 帧起步。硬件播放头开始推进，或已经开始播放且一次写入无法放下全部数据时，恢复 36,000 帧队列。首轮全屏对照仅依据播放头恢复，本地第二次切档窗口累计新增 6 次音频欠载，HTTP 第二次切档为 2.72825×。

截至释放，本地和 HTTP 累计音频欠载分别为 0、0 次。6/6 个稳态窗口无新增重缓冲，6/6 次切回后能暂停。每次重挂视图后均观察到匹配当前 Surface 的首帧。

渲染帧率取同一个解码器在稳态窗口内提交的输出帧数。60 Hz 面板放映 24 fps 样片时，3× 每秒对应 72 个源帧。该计数不直接测量面板呈现间隔。AAC 样片为静音，音频证据取自原生 AudioTrack 生效速率、音调和欠载计数。

## 对照与范围

本次调优限定在 MiTV-MTTP0 / API 28 的非 DRM 本地与网络点播，HLS 和 DASH 仍走各自的原有路径。该设备退出隧道后由 AudioTrack 按请求速度以原音调输出，PCM 保留 750 ms 目标及平台最小缓冲的四倍余量。Google AAC 解码器使用异步队列。渐进式输入每读取 64 KiB 重新检查加载目标，并在既有字节预算内保留最近两秒的压缩样本，供隧道切换时重新选择音视频轨道。

750 ms 缓冲配合同步 AAC 和更频繁的视频轮询时，3× 稳态提交帧率为本地 43.7、HTTP 43.0 帧/秒。换成异步 AAC 并恢复默认视频轮询后，分别为 53.8、52.0 帧/秒。600 ms 缓冲搭配异步 AAC 的本地对照出现 12 次欠载。

同样读取粒度、未保留两秒历史的对照中，HTTP 共收到 13 次请求。保留历史的对照减少到 4 次，切换速度期间无需重开请求。[调优对照](evidence/2026-11-21-android-mitv-playback-speed/comparisons.json)

旧版本 1.5× 的稳态仅为本地 0.81×、HTTP 0.81×，两个倍速窗口累计音频欠载分别达 198、189 次。切回 1× 后两边都停在缓冲，暂停超时。[此前同机记录](2026-11-21-android-mitv-api28.md)

只启用异步解码队列时，本地 1.5× 稳态为 0.84×，累计 188 次欠载。在隧道中向平台请求 1.5×，后 12 秒实测 0.98×。退出隧道并将变速交给 AudioTrack 后，同一段媒体稳态达到 1.50×。平台默认尺寸分配了 257,536 个 PCM 帧，750 ms 定长目标分配 36,000 帧。把目标压到 400 ms 的另一次对照出现了 3× 音频欠载。[调优对照窗口](evidence/2026-11-21-android-mitv-playback-speed/comparisons.json)

受控 HTTP 服务共记录 4 次请求。会话释放后，系统媒体资源服务对同一 PID 报告 0 个视频解码器。

复跑使用示例 Android armeabi-v7a Debug 构建，Dart 入口为 `integration_test/android_tv_playback_test.dart`，指定 `YL_TV_CASE=speed` 和 `YL_TV_HTTP_BASE`。每个计时窗口按请求速率 ±0.25× 校验，同时记录隧道实际状态、稳态视频帧推进、音频欠载、重缓冲和切回后的生命周期。
