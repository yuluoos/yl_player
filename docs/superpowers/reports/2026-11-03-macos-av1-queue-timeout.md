# macOS AV1 队列退出修复与持续显示对照

macOS AV1 尚未取得生产资格。本轮落地修复停止、停用和销毁中的队列取消顺序；持续显示仍失败，没有签发档位，也没有把正式矩阵的 AV1 两项改为通过。采集发生于本地 2026-11-02 晚间（UTC 11-03），设备 MacBookPro17,1 / 26A434。

## 已落地的修复

原顺序先停止呈现消费者，再等待解码线程退出，最后才清理帧队列。当解码线程正在等待满队列的容量时，这会等满 250 毫秒并记录一次 `enqueueTimeout`。这类清理阶段的掉帧不能用来解释之前的播放故障。

现在停止、停用先按新 generation flush 队列；销毁先 dispose 队列；然后才 join 并释放解码器。消费者停止后的生产者等待会由取消唤醒，不再靠超时结束。播放中的背压超时策略没有变动。

新增真实 demux/decoder wrapper 回归，使用容量为 1 的调度队列及同步输出的受控解码器，等待 `waitingEnqueues == 1` 后依次验证 stop、deactivate、dispose。修复前三个操作均产生 1 次掉帧；修复后该回归及已有停止/销毁、seek 代际回归共 **3/3 通过**。测试源同时同步到 iOS/macOS example。生成清单检查通过（iOS 902、macOS 951）；原 macOS 清单在既有提交新增 5 项时仅增加了 3，连同本次新增 1 项修正计数。没有重跑未受影响的全套测试，也没有声称 iOS 宿主本轮执行通过。

## 播放中超时的时序证据

隔离 arm64 Release example 仍使用单线程 dav1d、50 毫秒提前量、3 帧在途和 100 毫秒时钟有效期。长夹具重新生成，28,904 个视频包，PTS 间隔仅 41/42 毫秒；不能冒用此前临时夹具的哈希或资格记录。试验预算和日志插桩仅在证据副本中，未进入生产源码。

首次诊断约 10 秒时系统报告 240 帧、2 次掉帧，随后清理中超时。第二次诊断仅为采集后续因果链，系统掉帧会记录失败但不立即终止；它从首次掉帧起即已不合格，不能用于冻结预算或签发档位。

第二次诊断约 39 秒出现首次系统掉帧。附近音频时钟读取耗时 72 毫秒，但没有时钟过期或提交提前量不足的证据，不能断言这次读取导致显示丢帧。约 157.7 秒捕获一次 167.8 毫秒读取、时钟过期和恢复；同一窗口视频 worker 也有约 79 毫秒慢 tick。

约 161.35 秒，时钟再次过期；随后满队列等待超过 250 毫秒，出现播放中的 `enqueueTimeout`，清理又出现一次超时。系统日志记录同一时段默认音频设备切换到蓝牙耳机，AVAudioEngine 停止并重新配置。该事件明确区分了播放超时与后续清理超时；时间关联支持音频路由切换参与了这次停顿，但不证明所有历史超时同源。退出修复不等同于已修复音频设备切换或先前显示丢帧。

## 不含播放器的原生显示对照

独立 Swift/AppKit 程序预先加载 96 张 NV12 图像，使用 `AVSampleBufferDisplayLayer`、固定 host timebase、24 fps、50 毫秒提交窗口和 10 毫秒 timer。它不链接 Flutter 或播放器，不实时解码，不使用音频时钟。程序记录真实系统性能指标以及画面区域上方的窗口列表。

前两次对照在启动附近出现 1 次掉帧；其中一次增加了暂停预呈现。由于不能定位到具体图像，它们不能证明持续阶段有故障。第三次增加启动前计数，预先规定完整观察 4,320 帧，保留全部计数且不在第一次掉帧时结束。该轮前约 62 秒保持零掉帧，从总帧数 1,497 的 0 次变为 1,521 的 1 次；全程至该点最小提交提前量约 35.926 毫秒，采样时窗口可见、未锁屏、画面上方没有覆盖窗口。

完整三分钟结束时，系统累计 4,320 帧、1 次掉帧、0 损坏，进程按失败退出。系统图像队列日志也记录 1 次掉帧。这一对照证明持续显示丢帧也可出现在独立原生路径中，缩小了播放器侧排查范围。它仍不能区分 AVFoundation/Core Animation 内部行为、系统调度和更短时的外部干扰，不能直接宣称找到了系统缺陷或排除了所有瞬时遮挡。

## 剩余门禁

50 毫秒提前量、100 毫秒时钟有效期、零系统掉帧和双轮各 20 分钟条件均未放宽。持续显示根因仍需解决，随后才可进行同一精确制品的完整基线、冻结预算、独立复验、签发和正式本地/HTTP AV1 矩阵验收。原始失败均保留；本次 3 项回归通过不能替代这些门禁。
