# Apple DASH Load video caps — implementation and acceptance

The committed baseline is `d1b5b65`. This stage is included in the current strict Load-cap implementation commit. It adds strict video limits at DASH Load time on Apple for the existing bounded static clear AVC/AAC adapter. `YlLoadOptions.videoConstraints` travels with the accepted session through native preparation, constrained manifest compilation, and actual decoded-frame publication. A request that leaves any Period without a candidate fails with `decoder.quality_constraint_unsupported` before candidate media requests. A decoded frame whose display geometry exceeds the accepted cap fails its session before texture/native-surface/first-frame publication. Fixed public error text avoids forwarding URLs, headers, or injected closure prose.

The cap is the intersection of supplied width, height, and declared **video Representation** bitrate. The bitrate is neither audio-plus-video bandwidth nor measured network throughput. The constrained compiler validates the original program before filtering and admits a conservative family: compatible AVC codec/profile, role, display ratio and normalized frame rate, square pixels, and no color/dynamic-range/supplemental declarations; at most 16 quality identities. The unconstrained legacy route remains available. Selection remains automatic. The accepted cap cannot change during that DASH session: same-value `setVideoConstraints` succeeds, while changed or cleared values return `policy.video_constraints_reload_required`; a new Load may set a different cap. Runtime cap transactions and fixed Apple track selection remain future work.

## Whole-stage final fix — preserve ordinary HLS preferences during restoration

The final review found a shared-path regression outside immutable DASH policy: an ordinary headered-HLS constraint command could successfully change width320 to640 or clear it while a restoration manifest was being prepared, then the old prepared tuple overwrote both accepted intent and the restored AVPlayerItem preference. The behavioral RED (`/private/tmp/yl-dash-caps-finalfix-red.xcresult`, matching `.log`, exit65) recorded all four mismatches: accepted/item320 instead of640, and accepted/item320 instead of cleared/zero. The same regression confirmed that a fresh nil-options HLS Load must retain its own captured tuple despite changes made to the old session during preparation.

The final fix limits prepared-tuple assignment to new Loads and DASH restoration. Ordinary HLS restoration preserves the backend and coordinator preferences already acknowledged while preflight was pending. It changes only the two shared installation/commit assignments; DASH projection immutability, runtime rejection, initial Load capture, actual frame guards, and public schemas are unchanged.
