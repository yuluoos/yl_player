# 可选 DLNA 投屏包与 AirPlay 集成设计

状态：用户已于 2026-10-20 确认；实现与软件验证完成，真实接收端验收待执行。结果见 [验证记录](../reports/2026-10-20-optional-casting.md)。

## 目标与已确认范围

用户希望增加其他投屏协议，并考虑像 `yl_player_source_resolver` 一样将投屏能力拆成可选包。用户已明确移除 Google Cast，因此本次新增 DLNA，并集成现有 AirPlay 路径。

现有 AirPlay、RTMP/RTMPS 和脚本解析能力必须保持可用。本方案建议新增可选投屏包，并保持现有公开 API 兼容。以下方案作为本次实现边界；具体实现细节在计划中记录。

## 包的职责与依赖边界

| 包 | 职责与依赖 |
|---|---|
| `yl_player` | 保留本地播放和现有 AirPlay API，不反向依赖新投屏包。 |
| `yl_player_cast` | 提供可选的投屏控制器、能力查询、媒体源评估、远端会话状态、DLNA 实现和 AirPlay 适配入口。可以依赖 `yl_player`，绑定已有播放器并复用公开媒体源模型；不依赖脚本解析包。 |
| `yl_player_source_resolver` | 继续只负责将脚本解析为现有媒体源模型，解析结果可以交给本地播放或投屏。 |

本阶段将现有原生 AirPlay 实现保留在 `yl_player_apple` 中。新增 DLNA 不要求同时迁移播放器持有的 AVPlayer 生命周期及共享 FFmpeg 代码。因此，本次实现的是新增协议的可选安装，以及投屏控制入口的整合；尚不包含从播放器核心二进制中完全剥离 AirPlay。

保留 `YlLoadOptions(airPlay: true)`、现有 AirPlay 状态与设备选择器 API。

|---|---|---|---|

## 公开接口与会话行为

投屏控制器提供协议实现、设备发现状态、已发现设备、能力信息、媒体源评估及一个由控制器持有的远端会话。应用显式开始或停止设备发现，并选择已发现的 DLNA 设备。

AirPlay 继续通过系统选择器选择设备，不虚构可枚举的设备列表，也不承诺通过代码直接选择 AirPlay 设备。

远端会话提供加载、播放、暂停、停止、断开、音量和静音操作；只有在能力信息表明支持时才开放 seek。直播时长和不可获取的播放位置保持未知，不使用本地播放器事件伪造接收端首帧确认。

“断开控制连接”和“停止接收端播放”必须区分。API 允许调用方明确选择，并由协议实现报告不支持的操作语义。

每个会话内的命令串行执行。使用会话代次隔离旧回调、延迟到达的设备发现结果和失败的媒体替换操作。投屏尝试失败时，已有本地播放仍应可用。

提供可选、显式的本地转远端操作：记录本地媒体源、播放位置和播放意图，收到远端加载确认后才暂停本地播放，并提供显式返回本地的操作。断开后不自动切换接收端或重新开始播放。

返回本地在远端停止完成后再次检查取消代次、销毁、AirPlay 和本地会话身份；等待期间发生的新操作不能被旧源覆盖。取消后才完成的本地恢复只清理仍属于本次返回的会话。

发现状态按 provider ID 公开 `scanning` 与脱敏失败码，覆盖异步网络错误和重试。会话快照公开当前有效能力，包含托管媒体限制；示例持续监听这些状态，按能力启用控件。

### AirPlay 与 DLNA 的输出归属

AirPlay 仍是所绑定本地播放器的输出路由，不是另一个独立远端会话。AirPlay 激活时，视为占用该控制器的输出。

- AirPlay 激活期间启动 DLNA，返回路由冲突并保持当前播放；用户先通过系统选择器取消 AirPlay。
- 通过新适配入口启动 AirPlay 前，必须显式停止当前 DLNA 会话，或执行该会话支持的“断开但继续播放”。
- 若旧 API 在外部激活 AirPlay，新控制器只反映状态，不擅自认领该会话，也不静默停止已有接收端；出现冲突时提示调用方明确处理。
- 控制器销毁时，移除对外部持有的 AirPlay 会话的监听，不销毁调用方传入的播放器。清理由新入口创建的会话时，必须校验会话标识，避免影响后续会话。

## DLNA 协议实现

使用 SSDP 发现设备，限制扫描时长，并实现 UUID 去重、设备过期移除和取消操作。读取设备描述、服务描述及支持的协议信息，使用设备声明的服务类型与 URL，不硬编码服务路径。

同 UUID 的 LOCATION 变化时失效旧描述并重新获取，通过广告身份和扫描代次隔离旧响应；最多 8 个并行描述作业和 128 条设备广告。SOAP 按 UTF-8 字节长度显式设置 Content-Length。

通过 AVTransport 实现媒体加载、播放、暂停、停止、seek 和状态查询；通过 RenderingControl 实现音量和静音，并遵守设备声明的操作与取值范围。

持有会话期间，以受限请求和退避机制轮询状态；事件订阅可以后续增加。将 SOAP 故障映射为稳定错误，设备发现成功不能当作播放成功。销毁时关闭网络连接与定时器。

SSDP、XML 和 HTTP 响应均按不可信输入处理：限制大小、解析深度与超时，禁用外部实体，校验 HTTP(S) 控制地址，不向设备控制接口传播媒体源凭据。

文档说明宿主应用所需的局域网配置。iOS 组播 entitlement 和 Android 组播锁纳入平台集成；缺少授权不能静默解释为“没有设备”。

## 媒体交付与直播

分别评估两个问题：协议及设备是否兼容，以及接收端如何获取媒体。

接收端兼容的 HTTP(S) MP4/HLS 地址优先直接交给设备播放。并非所有 DLNA 设备都支持 HLS；未知能力保持“未验证”，拒绝时提供明确原因。直连地址必须能被接收端访问。请求头、DRM 和格式限制不得静默丢弃，也不得将任意媒体源凭据直接复制给设备。

### Apple 自定义直播交付

对于 Apple 平台上的 RTMP、RTMPS 和 HTTP-FLV 直播，将现有 H.264/AAC 滚动 HLS 生成器的生命周期整理为可复用的原生媒体交付资源，通过 Apple 适配器的可选能力暴露。

该资源继续负责解复用、转封装、受限存储和 HTTP 服务，沿用现有地址校验与 TLS 策略。解码流程保持独立；AirPlay 和 DLNA 可以消费同一类交付资源生成的 URL，不需要在后台隐藏播放一个 AVPlayer。

资源由会话持续持有，直到停止、替换或销毁；失败和取消必须可观察。

参数准入与资源替换分开，准入和实际 prepare 复用同一原生检查。拒绝新请求时保留已准入的准备和已接受租约。Dart 准入最多一个执行请求及一个最新排队候选；取消或销毁后的准入结果不得启动生产器。

对依赖应用本地媒体服务的投屏，明确不支持“断开但继续播放”：`canDetachKeepingPlayback` 为 `false`，调用时返回稳定错误 `cast.detach_unsupported`，同时保留当前直播会话。显式停止或销毁才释放资源。对于无需本地服务的直连 URL，可以在协议允许时支持断开控制后继续播放。

生成的 HLS/fMP4 只交给具备相应能力的接收端。测试必须验证接收端实际请求媒体，不能仅验证播放列表生成成功。本方案不承诺任意 DLNA 设备都能播放 RTMP 源，也不增加转码或 MPEG-TS 输出模式。

### Android 媒体范围

本次支持将接收端兼容的 HTTP 媒体地址直接投送给设备。现有直播转封装依赖 Apple 框架，因此本次不宣称 Android 支持 RTMP、RTMPS 或 HTTP-FLV 转 HLS；这些输入需要返回不支持的交付结果。

将直播转封装能力移植到 Android 属于独立的平台媒体工作。已有 Android 本地 RTMP 播放行为保持不变。

### 局域网媒体服务

适用时复用受限的本地 HTTP 服务，使用随机临时 URL，提供 GET、HEAD 和范围请求能力，并明确清理资源。

生成的媒体在局域网上通过明文 HTTP 传输；上游 RTMPS 的 TLS 不会加密这一段本地传输。网络接口变化时，应明确使交付资源失效并清理。本次不增加通用 HTTP 代理。

执行受影响的 Dart 测试、静态分析、公共 API 检查，以及 Apple/Android 原生构建。
